# Connected Telemonitoring Demo

A local IoT prototype for monitoring synthetic diabetes-related measurements. It simulates patient-side devices and gateways, transports their readings over MQTT, validates glucose observations in Node-RED, classifies them against configurable thresholds, and presents patient and alert state in a dashboard.

> **Important:** This is an educational and testing prototype, not a medical device or a clinical service. All patient records and measurements generated by the simulator are fictitious. Its thresholds, recommendations, and alert behavior must not be used for diagnosis or treatment.

## The Problem

Remote monitoring systems need to do more than receive measurements. They must associate each observation with a pseudonymous patient and device, reject malformed or unusable data, respect consent, detect concerning values and missing transmissions, and make the resulting state visible to a care team.

This project demonstrates that end-to-end path with synthetic data. It also provides controlled scenarios for exercising alerts, connectivity handling, data quality checks, and message loss without requiring physical sensors or a cloud service.

## Architecture

```text
Python simulator / patient gateway
  |  MQTT measurements, sequence numbers, gateway status (LWT)
  v
Mosquitto broker
  |  ctmc/patients/+/glycemie and ctmc/devices/+/status
  v
Node-RED flow
  |  validate -> check consent -> check plausibility -> classify / track connectivity
  +--> Dashboard 2.0 at /dashboard/ctsmc
  +--> MQTT alerts at ctmc/alertes/#
  +--> results/alerts.jsonl and results/audit.jsonl
```

The services run locally in Docker Compose. The Python simulator runs on the host and connects to the broker on `localhost:1883`.

### Components

- **Simulator (`simulator/`)**: Creates three pseudonymous patient profiles and synthetic glucose, blood pressure, pulse, and temperature readings. It acts as a gateway, publishes MQTT messages, tracks sequence numbers, and can inject test events.
- **Mosquitto (`mosquitto/`)**: MQTT broker configured for authenticated clients, persistent broker storage, and topic-based access control.
- **Node-RED (`nodered/`)**: Imports the committed flow from `flows.json`. It validates glucose messages, checks consent and plausibility, detects glucose and connectivity events, drives the dashboard, publishes alerts, and appends logs.
- **Results (`results/`)**: Host-mounted output files for simulator ground-truth events, alerts, and flow audit records.

## MQTT Topics and Messages

The project uses the `ctmc` topic root:

| Topic | Publisher | Purpose |
| --- | --- | --- |
| `ctmc/patients/<patient-id>/glycemie` | Simulator | Glucose observation; consumed by the current Node-RED workflow |
| `ctmc/patients/<patient-id>/tension` | Simulator | Blood pressure and pulse observations; currently published but not processed by Node-RED |
| `ctmc/patients/<patient-id>/temperature` | Simulator | Temperature observation; currently published but not processed by Node-RED |
| `ctmc/devices/GW-<patient-id>/status` | Simulator / broker LWT | Retained `online` or `offline` gateway state |
| `ctmc/alertes/<level>` and `ctmc/alertes/resolu` | Node-RED | New alerts, reminders, and resolved alerts |

Measurements are JSON objects containing a device ID and device specification, pseudonymous patient ID and profile, consent flag, UTC timestamp, sequence number, and an `observations` array. Observations include an IEEE 11073 / MDC code, numeric value, declared unit, UCUM unit, and quality. Glucose is published in `mg/dL`; the flow also accepts `mmol/L` and converts it to `mg/dL`. The dashboard displays both `mg/dL` and `g/L`, using `g/L = mg/dL / 100`.

The simulator publishes with MQTT QoS 1. Each gateway publishes a retained online status and registers `offline` as its Last Will and Testament (LWT), which lets the broker announce an unexpected gateway disconnect. On reconnect, the simulator flushes a bounded in-memory queue of messages that could not be sent while disconnected.

## Processing Flow

For glucose messages, the Node-RED flow runs these stages:

1. **Schema and identity checks**: Parse JSON, require the expected fields, verify that the patient ID in the payload matches the ID in the topic, validate the timestamp and glucose observation, and track sequence gaps.
2. **Consent**: Continue only when `consent` is exactly `true`. A rejected message is audited by pseudonymous ID and reason; it does not continue to classification or the accepted-measurement dashboard path.
3. **Plausibility and quality**: Require a `valid` quality value and a glucose result from 20 through 600 mg/dL. Rejected measurements are counted and logged for audit.
4. **Classification and alert state**: Convert the measurement to g/L, classify it, deduplicate ongoing alerts by patient, and resolve an active alert after the configured number of normal readings. Persistent alerts can be re-notified; a more severe classification can trigger a new notification.
5. **Connectivity monitoring**: An LWT `offline` status raises S01; a subsequent `online` status resolves it. A five-second watchdog raises S02 if a previously seen patient has not sent a glucose observation within the configured silence interval, unless the gateway is already marked offline.
6. **Outputs**: Update the dashboard, publish new/resolved alerts to MQTT, and append audit and alert records to JSON Lines files.

### Glucose Classification

Thresholds are defined in the Node-RED function in `nodered/flows.json`. They are demonstration rules and should be validated by qualified clinicians before any real-world use.

| Alert | Classification | Threshold |
| --- | --- | --- |
| A01 | Hypoglycemia, urgent | `< 0.70 g/L` (`< 70 mg/dL`) |
| A02 | Normal | `0.70–1.10 g/L` (`70–110 mg/dL`) |
| A03 | Monitor | `> 1.10 and < 2.00 g/L` (`> 110 and < 200 mg/dL`) |
| A04 | Elevated hyperglycemia | `2.00–< 2.50 g/L` (`200–< 250 mg/dL`) |
| A05 | Urgent hyperglycemia | `2.50–5.00 g/L` (`250–500 mg/dL`) |
| A06 | Critical hyperglycemia | `> 5.00 g/L` (`> 500 mg/dL`) |

The flow assigns severity levels and example recipient/action text to actionable alerts. These are simulated workflow labels, not real notifications to care providers.

## Dashboard

Open the Node-RED Dashboard 2.0 at <http://localhost:1880/dashboard/ctsmc>. The dashboard includes:

- A live glucose chart by patient, with reference lines at 70 and 250 mg/dL.
- Patient profile, latest glucose values, classification, gateway state, and time since last message.
- Counts of accepted and rejected glucose messages and detected sequence gaps.
- Active alerts, rejected-data reasons, and a short in-memory alert history.

Dashboard aggregates and history are held in Node-RED flow context and reset when the runtime restarts. The JSONL output files are append-only and remain in the host `results/` directory.

## Requirements

- Docker Desktop with Docker Compose available as `docker compose`.
- Python 3.9 or later and `pip` for the simulator.
- Ports `1880` and `1883` available on the host.

## Run Locally (Windows PowerShell)

Run these commands from the repository root (`telesurveillance-connecte`):

1. Create the local environment file:

	```powershell
	Copy-Item env.example .env
	```

	`.env` supplies `MQTT_PASSWORD` to Node-RED. The example value is for local demonstration only. The MQTT credentials in `mosquitto/config/passwd` must match the password used by the simulator and Node-RED; update the broker's hashed credentials as well if you change it. Do not commit `.env` or use demo credentials outside a private local environment.

2. Start the broker and Node-RED:

	```powershell
	docker compose up -d
	docker compose ps
	```

	The compose file passes `MQTT_PASSWORD` into the Node-RED container, but the checked-in `nodered/flows_cred.json` currently stores the literal `${MQTT_PASSWORD}` string. Verify that Node-RED resolves this to the actual password. If the broker reports an authentication failure, open the editor at <http://localhost:1880>, edit the Mosquitto MQTT broker configuration, set username `nodered` and the same password as `MQTT_PASSWORD`, then deploy. The simulator connects as `simulator` and must use that same password.

3. Install the simulator dependency in a virtual environment:

	```powershell
	python -m venv .venv
	.\.venv\Scripts\Activate.ps1
	python -m pip install -r simulator/requirements.txt
	```

4. Set the same MQTT password and start the simulator:

	```powershell
	$env:MQTT_PASSWORD = "NodeMDP123"
	python simulator/simulator.py --scenario normal
	```

	The default run simulates three patients for four minutes, publishing glucose every five seconds and blood pressure/pulse and temperature every six simulation steps. Press `Ctrl+C` to stop early. Visit the dashboard URL above in a browser.

To stop the containers while preserving mounted data and results:

```powershell
docker compose down
```

For Command Prompt, set the variable with `set MQTT_PASSWORD=NodeMDP123` and use `python simulator\simulator.py --scenario normal`.

## Simulator Scenarios

Use `python simulator/simulator.py --scenario <name>` from the repository root. Unless noted, scenarios use the default three patients, 5-second interval, and 240-second duration.

| Scenario | Behavior |
| --- | --- |
| `normal` | Baseline readings, including periodic synthetic post-meal glucose rises |
| `hypoglycemia` | Lowers glucose and raises pulse for patient `P-7f3a9c` |
| `hyperglycemia` | Raises glucose for patient `P-2b81d4` |
| `hyperglycemia_critical` | Raises glucose to a critical simulated range for patient `P-2b81d4` |
| `sensor_offline` | Abruptly disconnects the gateway for patient `P-c04e57`, then restarts it |
| `implausible` | Injects out-of-range glucose values for patient `P-2b81d4` |
| `no_consent` | Publishes measurements with consent disabled for patient `P-c04e57` |
| `packet_loss` | Randomly drops messages; default loss rate is 30% |
| `broker_down` | Manual broker interruption scenario; stop and restart Mosquitto yourself while the simulator is running |

Anomaly timing, duration, ramp, patient count, seed, and message loss can be adjusted with command-line options. See:

```powershell
python simulator/simulator.py --help
```

For example, run a shorter hypoglycemia test with a reproducible random seed:

```powershell
python simulator/simulator.py --scenario hypoglycemia --interval 2 --duration 120 --seed 42
```

The `--dry-run` option prints generated MQTT topics and payloads without connecting to a broker:

```powershell
python simulator/simulator.py --scenario hypoglycemia --dry-run
```

For the manual broker scenario, leave the simulator running in one terminal and use another:

```powershell
docker compose stop mosquitto
docker compose start mosquitto
```

## Results and Evaluation

- **`results/events.csv`**: Simulator ground truth, including run start/end, anomaly start/end, dropped messages, injected glitches, and gateway/broker connectivity events. This can be compared with flow output to estimate detection rate, false positives, and detection latency.
- **`results/alerts.jsonl`**: One JSON object per alert, reminder, or resolution.
- **`results/audit.jsonl`**: One JSON object per accepted/rejected measurement or alert decision. Depending on the event, records can include a pseudonymous patient ID, classification, sequence gap, reason, and measurement value.

These files are append-only across runs. Copy or rotate them before a new evaluation if you need an isolated result set. The simulator writes its ground-truth events to `results/events.csv` by default; Node-RED writes alert and audit files inside the container to the mounted `results/` directory.

## Configuration

- **MQTT password**: `env.example` provides a local example value. Compose passes `MQTT_PASSWORD` to Node-RED; the simulator reads it from the shell environment or prompts for it. The Node-RED broker credential is stored separately in `nodered/flows_cred.json`, so verify it uses the same value. Mosquitto verifies the usernames/passwords configured in `mosquitto/config/passwd`, and `mosquitto/config/acl` restricts each account to specific topic paths.
- **Node-RED thresholds and workflow**: Edit and deploy the functions in `nodered/flows.json`. The flow file is mounted into `/data` and is the runtime's configured flow.
- **Connectivity and alert timing**: `docker-compose.yml` currently sets `SILENCE_THRESHOLD_S=20`, `RENOTIFY_S=60`, and `CLEAR_N=2` for Node-RED.
- **Simulator controls**: Run `python simulator/simulator.py --help` for interval, duration, anomaly timing, patient count, random seed, host, port, and event-file options.

## Current Scope and Limitations

- All measurements are generated data. The simulator models IEEE 11073-style device metadata and MDC codes; it does not connect to physical medical devices.
- The current Node-RED workflow processes glucose topics and gateway status. Blood pressure, pulse, and temperature are generated and published but have no validation, alerting, or dashboard processing flow yet.
- MQTT is configured on port 1883 without TLS. Although the simulator has optional TLS client flags, this Compose broker configuration does not provide a TLS listener or certificates.
- Node-RED editor and dashboard authentication are not enabled in `settings.js`. Keep this setup on a trusted local machine/network; do not expose it directly to the internet.
- The example broker and Node-RED setup is for development, not production. A real deployment needs hardened secrets, TLS, access controls, protected dashboards, monitoring, retention/backup policies, privacy review, and clinically validated thresholds and escalation procedures.
- The flow's sequence tracking and dashboard state are runtime context, not a durable clinical data store. Restarting Node-RED resets those in-memory aggregates.
